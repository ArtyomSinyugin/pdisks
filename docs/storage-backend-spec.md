# ТЗ: `storaged-ng` — бэкенд управления дисковой подсистемой Linux

**Версия:** 1.0
**Статус:** проект спецификации
**Аудитория:** разработчики бэкенда, авторы инсталляторов и UI, интеграторы дистрибутивов

---

## 0. Резюме

Единый бэкенд, который заменяет собой разрозненный зоопарк (`blivet`, `curtin`, `libstorage-ng`, `udisks2`, самописные скрипты инсталляторов) и покрывает весь стек: таблицы разделов, файловые системы, LVM, mdadm, LUKS, ZFS, Btrfs, bcache/dm-cache, сетевые устройства (iSCSI, NVMe-oF, RBD, DRBD, NBD), multipath, зональные устройства, съёмные носители.

**Центральная идея.** Дисковая подсистема моделируется как **типизированный направленный ациклический граф**, а работа с ним строится как компилятор:

```
Probe (текущее состояние) ─┐
                           ├─► Diff ─► Plan (DAG действий) ─► Execute
Spec (желаемое состояние) ─┘              │
                                          └─► Validate / Visualize / Review
```

Из этого следуют три свойства, ради которых всё затевается:

1. **План — это данные.** Сериализуемый объект, который можно показать, сохранить, отревьюить, проиграть в dry-run, сравнить в CI. Не «набор функций, которые сейчас что-то сделают».
2. **Желаемое состояние декларативно.** Пользователь описывает результат, а не последовательность шагов. Из этого бесплатно получается replan при hotplug и идемпотентность.
3. **Ядро не знает ни про LVM, ни про ZFS.** Всё технологическое знание живёт в провайдерах-плагинах, которые декларируют свои возможности машиночитаемо.
4. **Совместимость — система типов, а не список проверок.** Структурно корректный граф может описывать неработоспособную конфигурацию (зеркало из двух разделов одного диска). Вывод атрибутов в двух направлениях плюс алгебра доменов отказа ловит это единым механизмом — и в обратную сторону отвечает на вопрос «что сюда можно положить», из-за чего UI не способен предложить несовместимый вариант.

### Цели

- Полное покрытие перечисленных технологий без «особых случаев» в ядре
- Точный dry-run по тому же кодовому пути, что и реальное выполнение
- Машиночитаемая диагностика с предлагаемыми исправлениями
- Контракт визуализации: UI не должен догадываться о структуре
- Транзакционность: журнал, откат где возможно, явная «точка невозврата»
- Паритет CLI / GUI / API — все три поверх одной библиотеки

### Не-цели

- Управление файлами внутри ФС (это не файловый менеджер)
- Мониторинг здоровья дисков (SMART — отдельный сервис, бэкенд только потребляет)
- Собственная реализация файловых систем и RAID (только оркестрация существующих)
- Кластерные блокировки (GFS2/OCFS2 — вне периметра v1)

## 1. Терминология

| Термин | Значение |
|---|---|
| **Node** | Узел графа: диск, раздел, ФС, VG, LV, пул, датасет, кэш и т.д. |
| **Edge** | Типизированное ребро между узлами |
| **Graph** | Полный DAG текущего либо желаемого состояния |
| **Probe** | Сканирование системы → `Graph(current)` |
| **Spec** | Декларативное описание `Graph(desired)` |
| **Plan** | DAG действий, переводящий current → desired |
| **Action** | Атомарная операция (создать раздел, mkfs, добавить PV…) |
| **Provider** | Плагин, реализующий работу с одной технологией |
| **Capability** | Машиночитаемое свойство узла или провайдера |
| **Diagnostic** | Структурированное сообщение валидатора |

## 2. Доменная модель

### 2.1 Почему граф, а не дерево

Классическая ошибка инсталляторов — моделировать хранилище деревом «диск → раздел → ФС». Это ломается сразу:

- N физических томов → одна VG → M логических томов (many-to-many)
- Btrfs-ФС лежит на нескольких устройствах и предоставляет несколько подтомов
- `zvol` — блочное устройство, **предоставляемое** пулом, поверх которого может быть ещё один LUKS и ещё одна ФС
- bcache имеет два входа с разной семантикой (backing и cache)
- multipath объединяет несколько путей в один узел

Модель — **DAG**. Ацикличность проверяется валидатором как инвариант (случай `zvol → LUKS → ФС` цикла не создаёт, но вложенный пул поверх собственного zvol — создаёт, и должен отклоняться).

### 2.2 Node

```
Node {
  id:          NodeId            // стабильный, см. 2.4
  kind:        NodeKind          // см. 3
  provider:    ProviderId
  state:       NodeState         // Present | Planned | ToDestroy | Missing | Foreign | Anomalous
  anomalies:   [Anomaly]         // см. 2.7
  size:        Option<Bytes>     // ёмкость, предоставляемая узлом
  used:        Option<Bytes>     // занято (если известно)
  alignment:   Alignment
  identity:    IdentitySet       // uuid, label, wwn, serial, partuuid...
  attrs:       Map<Key, Value>   // типизированные атрибуты провайдера
  caps:        CapabilitySet     // см. 3.2
  health:      Health            // Ok | Degraded{...} | Failed{...} | Unknown
  flags:       NodeFlags         // removable, network, readonly, zoned, encrypted...
  holders:     [NodeId]          // кто использует (вычисляется)
}
```

**Правило:** `size` — то, что узел *отдаёт наверх*, а не то, что занимает снизу. У LUKS-контейнера `size` меньше размера раздела на величину заголовка. Это устраняет вечную путаницу «почему у меня 500 ГБ, а видно 498».

### 2.3 Edge

```
Edge { from: NodeId, to: NodeId, kind: EdgeKind, role: Option<Role> }
```

Типы рёбер (закрытый список, ядро понимает семантику каждого):

| EdgeKind | Смысл | Пример |
|---|---|---|
| `Contains` | физическое вложение с offset | диск → раздел |
| `Backs` | узел является носителем для узла сверху | раздел → LUKS |
| `MemberOf` | член множества с избыточностью/агрегацией | PV → VG, диск → md |
| `Provides` | контейнер порождает сущность | VG → LV, пул → датасет |
| `Caches` | кэширующая связь | SSD → bcache |
| `Journals` | внешний журнал/лог | SLOG → пул |
| `Spare` | горячий резерв | диск → md |
| `Path` | физический путь к тому же устройству | sdb → mpatha |
| `Replicates` | сетевая репликация | локальный LV → DRBD |

`role` уточняет: `data | metadata | parity | cache-read | cache-write | log | special | spare`.

Разделение `Contains` / `Backs` / `MemberOf` существенно: только `Contains` несёт offset и участвует в проверке перекрытий; только `MemberOf` участвует в расчёте избыточности; `Backs` — чистая композиция один-к-одному.

### 2.4 Идентичность

**Kernel name (`/dev/sda`) идентичностью не является никогда.** Это волатильный атрибут, наравне с текущей температурой.

`NodeId` вычисляется из контента:

| Класс узла | Источник идентичности (по приоритету) |
|---|---|
| Диск | `WWN` → `id_serial` → `by-path` → синтетический |
| Раздел | `PARTUUID` (GPT) → `(disk_id, index)` (MBR) |
| ФС | `UUID` → `(backing_id, "fs")` |
| LUKS | header `UUID` |
| PV / VG / LV | нативные UUID LVM |
| md | md UUID из суперблока |
| ZFS пул / датасет | GUID пула, полное имя датасета |
| Btrfs | fsid + subvolume UUID |
| Сетевые | `(транспорт, target IQN/NQN, LUN)` |
| Планируемые | `planned:<ULID>` |

При выполнении плана `planned:` ID **сохраняется как алиас** к реальному ID — чтобы UI не терял выделение и прогресс не «перескакивал» на другой объект.

### 2.5 Размеры и выравнивание

Байты — целые (`u64`), никогда с плавающей точкой. Форматирование в человеческий вид — задача слоя представления, ядро отдаёт байты.

```
SizeSpec =
  | Exact(Bytes)
  | Percent(Ratio, of: Reference)      // of: disk | vg | remaining
  | Range { min: Bytes, max: Option<Bytes>, weight: u32 }
  | Fill                                // = Range{0, None, weight: 1}
  | Auto                                // провайдер предлагает по эвристике роли
```

```
Alignment { grain: Bytes, offset: Bytes }
```

Выравнивание **распространяется снизу вверх** и агрегируется как НОК: physical block size → optimal_io_size → ширина страйпа RAID → размер зоны у zoned → требования провайдера сверху. Провайдер декларирует `required_alignment()`; планировщик обязан удовлетворить объединение всех требований по цепочке. Дефолт нижней границы — 1 МиБ.

Отдельно фиксируется: LUKS2 добавляет offset данных (по умолчанию 16 МиБ), mdadm 1.2 — свой, LVM — свой. Все они декларируются провайдером как `overhead(size) -> Bytes`, и `size` узла сверху вычисляется, а не угадывается.

### 2.6 Модель монтирования — отдельный слой

Точки монтирования **не являются** свойством узла графа. Это отдельная модель:

```
MountEntry {
  source:     MountSource     // NodeRef | Subvolume | Dataset | Bind | Tmpfs | Network
  target:     Path
  fstype:     String
  options:    [MountOption]   // типизированные, не строка
  identity_by: IdBy           // Uuid | PartUuid | Label | Path | DPS
  passno:     u8
  depends_on: [NodeId]        // для генерации systemd-ordering
}
```

Причина разделения: одна ФС монтируется в несколько мест (bind, подтома Btrfs), а точки монтирования существуют и без блочных устройств (tmpfs, NFS, virtiofs). Смешивание этих сущностей — источник половины багов в существующих инсталляторах.

### 2.7 Модель описывает, а не утверждает

Естественное желание — сделать несовместимые конфигурации непредставимыми: конструктор возвращает `Result`, невалидный граф не существует, целый класс ошибок исчезает по построению. Для этой предметной области решение неверное.

**Причины:**

1. **Probe обязан описывать реальность, а реальность регулярно невалидна.** Зеркало из двух разделов одного диска, деградировавший массив, VG без одного PV, осиротевший LUKS-заголовок, GPT с битой резервной копией. Если модель этого не выражает — инструмент не может показать, а значит, не может помочь починить. Утилита, отказывающаяся загрузить сломанный диск, бесполезна ровно тогда, когда за ней тянутся.
2. **Валидность — свойство тройки `(граф, среда, политика)`, а не узла.** `ext4` безупречен над NVMe и невозможен над host-managed SMR; один и тот же граф валиден для одного целевого ядра и сломан для другого. Конструктор не может проверить то, чего в момент конструирования ещё нет.
3. **Валидность не инвариант во времени.** Диск умер — граф стал невалидным без единого вызова конструктора.
4. **Редактирование — процесс.** Ползунок размера проходит через невалидные промежуточные состояния. Запрет породит теневую «черновую» модель, то есть ту же пермиссивную с лишним слоем.
5. **Граница не линия, а градиент.** `Unsafe` обязано быть конструируемым: Btrfs RAID5 — осознанно принимаемый риск, а не запрет.

**Принцип разграничения:**

> По построению запрещается то, чему нет референта в реальности. Всё, что бывает на настоящих дисках, представимо и подлежит оценке.

| Отклоняется на входе (malformed) | Принимается и помечается (invalid) |
|---|---|
| Цикл в графе | Перекрывающиеся разделы в битом GPT |
| Ребро `Caches` от ФС к диску | Зеркало из двух разделов одного диска |
| Висящая ссылка на `NodeId` | Массив без кворума, ФС с грязным журналом |
| Отрицательный размер | ext4 на drive-managed SMR |
| Секрет в сериализуемой структуре | Несогласованные метаданные LVM |

**Аномалии — первоклассная сущность.** Реальность, нарушающая ожидания, не отбрасывается, а фиксируется на узле:

```
Anomaly {
  code:       "A_GPT_BACKUP_CORRUPT" | "A_OVERLAPPING_PARTITIONS" | ...
  severity:   Info | Warning | Critical
  repairable: bool
  fixes:      [Fix]
  evidence:   Map           // сырые данные для отчёта
}
```

Аномалии участвуют в контракте визуализации наравне с остальным (badge `Anomalous`) и блокируют деструктивные операции над затронутым поддеревом до явного подтверждения.

**Валидность как токен-доказательство.** «Непредставимость» возвращается, но на границе подсистем, а не в конструкторе:

```
Graph                      // описательный, допускает любую реальность
  └─ typecheck(env, policy) -> Result<Checked<Graph>, [Diagnostic]>
       └─ Plan::build(Checked<Graph>, Checked<Graph>) -> Plan
            └─ Executor::apply(Plan, generation) -> ...
```

`Checked` не имеет публичного конструктора и получается только прогоном проверки из главы 7 с явной политикой. Исполнитель физически не принимает непроверенный граф; при смене среды или политики токен недействителен и требуется повторная проверка. Модель остаётся описательной, API — конструктивным, а гарантия даётся там, где она осмысленна.

## 3. Таксономия узлов и возможностей

### 3.1 NodeKind

```
Disk | LoopDevice | ZramDevice | NetworkBlockDevice | MultipathDevice
PartitionTable | Partition | FreeSpace
LuksContainer | IntegrityDevice | VerityDevice
MdArray | LvmPv | LvmVg | LvmLv | LvmThinPool | LvmCachePool
BcacheDevice | DmCache | DmWritecache
Filesystem | Swap
BtrfsFilesystem | BtrfsSubvolume
ZfsPool | ZfsVdev | ZfsDataset | ZfsVolume
DrbdResource
```

`FreeSpace` — полноценный узел, а не отсутствие узла. Это позволяет UI отрисовать свободное место как объект, а планировщику — размещать в нём разделы с явными ограничениями.

### 3.2 Capability — вместо `if kind == XFS`

Ядро не содержит ни одного условия по конкретной технологии. Провайдер декларирует:

```
Capabilities {
  resize:        { grow_online, grow_offline, shrink_online, shrink_offline: bool }
  size_limits:   { min: Bytes, max: Bytes }
  discard:       { supported: bool, passthrough: bool }
  redundancy:    Option<{ level, min_members, tolerated_failures(n) }>
  boot:          { firmware: [Uefi|Bios|Prep], loaders: [Grub|SdBoot|Uboot] }
  labels:        { max_len, charset, case_sensitive }
  write_pattern: Random | SequentialWithinZone
  cow:           bool
  checksums:     bool
  multi_device:  { min, max }
  heterogeneous_members: bool      // Btrfs — да, mdadm — нет
  requires_contiguous: bool
  maturity:      Stable | Experimental | Discouraged{reason_key}
}
```

Примеры, которые из этого автоматически следуют без единой строчки специального кода:

- XFS: `shrink_* = false` → валидатор отклоняет уменьшение с внятным кодом
- Btrfs RAID5: `maturity = Discouraged{"btrfs.raid56.write_hole"}` → предупреждение и требование явного подтверждения
- Btrfs: `heterogeneous_members = true` → диски разного размера разрешены; mdadm — нет
- Zoned SMR: `write_pattern = SequentialWithinZone` → любая ФС без соответствующей capability отклоняется на этом устройстве

**Требование:** матрица возможностей версионируется и покрыта тестами против реальных версий утилит. Если `xfsprogs` в системе старее требуемой, провайдер обязан скорректировать свои caps во время инициализации (feature detection), а не полагаться на константы времени сборки.

## 4. Архитектура провайдеров

```
┌──────────────────────────────────────────────────────────┐
│  API: D-Bus │ JSON-RPC (unix socket) │ CLI │ Rust/C lib  │
├──────────────────────────────────────────────────────────┤
│  Orchestrator: Probe · Validate · Solve · Plan · Execute  │
├──────────────────────────────────────────────────────────┤
│  Core: Graph · Types · Capabilities · Diagnostics         │
├──────────────────────────────────────────────────────────┤
│  Provider Registry                                        │
│  gpt · mbr · ext4 · xfs · btrfs · zfs · lvm · md · luks   │
│  bcache · dm-* · iscsi · nvmeof · rbd · drbd · multipath  │
├──────────────────────────────────────────────────────────┤
│  System Adapters: libblkid libfdisk libdevmapper udev     │
│                   sysfs  netlink  typed CLI wrappers      │
└──────────────────────────────────────────────────────────┘
```

### 4.1 Интерфейс провайдера

```
trait Provider {
    fn id() -> ProviderId;
    fn kinds() -> [NodeKind];

    // инициализация: определить доступность и версии инструментов
    fn probe_environment() -> ProviderEnv;   // + скорректированные caps

    // обнаружение
    fn scan(ctx: &ProbeCtx) -> Result<[Node], [Edge]>;

    // декларации
    fn capabilities(node: &Node) -> Capabilities;
    fn required_alignment(node: &Node) -> Alignment;
    fn overhead(requested: Bytes, params: &Params) -> Bytes;

    // валидация своих узлов
    fn validate(node: &Node, graph: &Graph) -> [Diagnostic];

    // планирование
    fn plan_create(spec: &NodeSpec, ctx: &PlanCtx) -> [Action];
    fn plan_destroy(node: &Node, ctx: &PlanCtx) -> [Action];
    fn plan_modify(from: &Node, to: &NodeSpec, ctx: &PlanCtx) -> [Action];

    // выполнение
    fn execute(action: &Action, ctx: &mut ExecCtx) -> Result<Effect>;
    fn rollback(action: &Action, ctx: &mut ExecCtx) -> Result<()>;
}
```

### 4.2 Правила для провайдеров

- **Приоритет библиотек над CLI.** `libblkid`, `libfdisk`, `libdevmapper`, `libzfs` — там, где есть. CLI — только через типизированные адаптеры с версионированными парсерами и обязательным предпочтением машиночитаемого вывода (`--json`, `--reportformat json`, `lsblk -J`).
- **Парсинг человеческого вывода запрещён**, кроме случаев, где альтернативы нет; такие места помечаются `#[fragile]`, покрываются golden-тестами на выводах нескольких версий утилиты и фиксируются в реестре технического долга.
- **Провайдер не трогает ничего вне своих узлов.**
- **Каждый `execute` идемпотентен либо декларирует, что нет.**
- Провайдеры загружаются динамически; отсутствие `zfs` в системе не должно приводить к падению, только к недоступности соответствующих узлов с внятной диагностикой.

## 5. Подсистема обнаружения (Probe)

### 5.1 Порядок

1. **Транспортный слой.** Локальные шины (sysfs), сетевые сессии (`iscsiadm`, `nvme list-subsys`, RBD, DRBD). Фиксируется `transport`, `reachable`, `latency_class`.
2. **Дедупликация путей.** `multipathd`/WWID/NGUID — до всего остального. Узел-`Path` помечается `hidden_by: mpathX`. Работа с отдельными путями напрямую запрещается валидатором.
3. **Геометрия и топология.** `logical/physical_block_size`, `optimal_io_size`, `alignment_offset`, `rotational`, `removable`, `zoned`, `nr_zones`, `zone_size`, `max_open_zones`.
4. **Содержимое.** Подписи через `libblkid`, таблицы разделов, суперблоки.
5. **Верхние слои.** LVM, md, LUKS, bcache, ZFS, Btrfs, DM-дерево (`dmsetup ls --tree` как источник рёбер).
6. **Использование.** Держатели, монтирования, открытые файлы, swap.
7. **Сборка графа + верификация инвариантов.**

### 5.2 Требования

- **Probe не изменяет систему.** Никакой автосборки массивов, никакого `vgchange -ay` по своей инициативе. Активация — только явное действие в плане.
- **Инкрементальность.** Полный скан больших SAN-конфигураций может занимать десятки секунд; после первого раза обновления приходят из udev/netlink и применяются точечно.
- **Bounded latency.** Сетевые устройства опрашиваются с таймаутами; недостижимый iSCSI-таргет даёт узел в состоянии `Missing` за отведённое время, а не блокирует probe.
- **Фикстуры.** Полный дамп probe сериализуется в JSON и может быть загружен обратно. Это основной инструмент воспроизведения багов: пользователь присылает дамп, разработчик воспроизводит граф и план без железа.

### 5.3 Особые случаи

| Ситуация | Обязательное поведение |
|---|---|
| Multipath | Дедуплицировать до анализа содержимого, иначе получим «два одинаковых диска» |
| Degraded md/пул | Узел `Health::Degraded`, флаг `partially_assembled`, деструктивные операции блокируются |
| Foreign / чужие ОС | `NodeState::Foreign`, распознавание Windows/macOS/других Linux, защита по умолчанию |
| Zoned | Разбор зон, `write_pointer`, запрет несовместимых ФС |
| Съёмный носитель | Флаг `removable`, генерация плана с `nofail` по умолчанию |
| Устройство исчезло | `Missing`, не удаление узла: план и выделение в UI не должны разваливаться |
| Активный LUKS | Различать «контейнер» и «открытое отображение», не считать двумя устройствами |

## 6. Декларативная спецификация желаемого состояния

Формат — YAML/JSON с версионированной JSON Schema. Он же используется как язык автоустановки (kickstart/preseed-замена) и как сохраняемый профиль разметки.

```yaml
version: 1

defaults:
  alignment: 1MiB
  filesystem: btrfs
  discard: periodic          # off | periodic | inline

selectors:
  primary:
    match: { rotational: false, min_size: 200GiB, removable: false }
    require_unique: true      # ошибка, если подходит != 1 устройству

layout:
  - disk: "@primary"
    wipe: true
    table: gpt
    partitions:
      - role: esp
        size: 1GiB
        mount: /efi
      - role: boot
        size: 2GiB
        fs: ext4
        mount: /boot
      - role: root
        size: { min: 64GiB, weight: 1 }   # заполнить остаток
        encrypt:
          type: luks2
          keyslots: [{ passphrase: "@prompt:disk-password" }]
          unlock: [tpm2, passphrase]
          allow_discards: true
        fs:
          type: btrfs
          compression: zstd:1
          subvolumes:
            - { name: "@",         mount: / }
            - { name: "@home",     mount: /home }
            - { name: "@log",      mount: /var/log, options: [nodatacow] }
            - { name: "@snapshots", mount: /.snapshots }

  - pool:
      name: tank
      type: zfs
      vdevs:
        - { type: raidz2, members: { match: { model: "ST18000*" }, count: 6 } }
        - { type: special, layout: mirror, members: "@nvme-pair" }
      datasets:
        - { name: tank/data, mount: /srv/data, compression: lz4, quota: 8TiB }

swap:
  strategy: zram             # zram | file | partition | none
  size: { percent: 50, of: ram, max: 8GiB }

policy:
  allow_destructive: explicit    # never | explicit | auto
  protect_foreign_os: true
  require_confirmation_for: [Discouraged, Irreversible]
```

### Требования к формату

- **Селекторы вместо имён устройств.** `@primary` разрешается во время планирования; `/dev/sda` в спеке допустим, но помечается предупреждением как нестабильный.
- **Роли (`role: esp|boot|root|home|swap|...`)** несут семантику: провайдер знает дефолтные размеры, типы GUID, флаги, опции монтирования. `role: esp` не требует ручного указания FAT32 и типа раздела.
- **Секреты не хранятся в спеке.** Только ссылки `@prompt:`, `@file:`, `@tpm2:`, `@keyring:`.
- **Спека — вход и выход.** Бэкенд умеет сериализовать текущее состояние обратно в спеку (`export`), что даёт: воспроизведение конфигурации на другой машине, diff между машинами, документирование.

## 7. Система типов и совместимость узлов

Структурная корректность графа (ацикличность, отсутствие перекрытий, сходимость размеров) **не означает работоспособность**. Граф может быть безупречен структурно и при этом описывать конфигурацию, которая не соберётся, не загрузится или тихо потеряет данные.

Канонический пример: зеркало из `sda1` и `sda2`. DAG корректен, члены одного размера, mdadm соберёт массив без единого возражения — и это не избыточность вообще. Ни одна capability-матрица такого не ловит, потому что проблема не в свойствах узлов, а в **отношении между ними**.

Поэтому совместимость — не список правил валидатора, а **система типов над графом** с выводом атрибутов в двух направлениях. Правила валидатора при таком подходе становятся тонким слоем поверх типовой проверки, а не её заменой.

### 7.1 Классы несовместимости

| Класс | Природа | Пример |
|---|---|---|
| **Вертикальная** | Узел не может лежать поверх узла | ext4 на host-managed SMR; PV внутри ESP; LUKS на CD-ROM |
| **Горизонтальная** | Члены агрегата несовместимы между собой | 512e + 4Kn в одном vdev; разный ashift; локальный диск + iSCSI в одном md |
| **Транзитивная** | Свойство теряется или конфликтует по цепочке | discard заблокирован LUKS'ом на третьем слое; выравнивание не проходит сквозь стек |
| **Топологическая** | Отношение узлов делает конструкцию бессмысленной | зеркало из двух разделов одного диска; RAID поверх двух LUN одного массива |
| **Средовая** | Конфигурация корректна, но нереализуема здесь и/или там | GRUB не читает zstd; целевое ядро не смонтирует ФС, созданную свежим `mkfs` |
| **Временная** | Конечное состояние валидно, промежуточное — нет | усечение ФС ниже занятого объёма на промежуточном шаге плана |

Ядро обязано ловить все шесть классов **одним механизмом**, иначе каждый новый провайдер приносит свой набор частных проверок, и покрытие неизбежно расползается.

### 7.2 Интерфейсы вместо списка допустимых пар

Матрица «что на что можно класть» комбинаторно неподъёмна и мертва при добавлении провайдера. Вместо неё — структурная типизация.

Каждый узел **предоставляет** и **требует** типизированные интерфейсы:

```
Interface {
  name:  BlockDevice | Storage | Mountable | KeySource | CacheTarget | ...
  attrs: Map<AttrKey, AttrValue>
}

Provider::offers(node)  -> [Interface]
Provider::requires(node) -> [InterfaceDemand]
```

Ребро допустимо тогда и только тогда, когда предложение удовлетворяет требование по правилам подтипирования (уточняющих типов над атрибутами):

```
offer ⊨ demand
```

Это даёт три вещи сразу: новый провайдер не требует правок ядра; проверка одинакова для всех технологий; и — главное — работает **в обратную сторону** (см. 7.11).

### 7.3 Атрибуты как решётка

Чтобы атрибуты можно было сливать и сравнивать автоматически, каждый обязан образовывать решётку с определёнными `join`/`meet`. Провайдер не пишет код слияния — он декларирует правило.

| Атрибут | Направление | Слияние | Что ловит |
|---|---|---|---|
| `logical_sector`, `physical_sector` | ↑ | `max` | 512e + 4Kn в массиве |
| `write_pattern` | ↑ | `join` (Random ⊑ SeqInZone) | ФС на SMR/ZNS |
| `transport` | ↑ | `union` | локальный + сетевой в одном RAID |
| `latency_class` | ↑ | `max` | таймауты стека |
| `hotplug_risk` | ↑ | `max` | mdadm на флешке |
| `discard_capable` | ↑ | `and` | TRIM не доходит до SSD |
| `failure_domains` | ↑ | `union` | см. 7.6 |
| `redundancy` | ↑ | `min` по членам | асимметрия избыточности |
| `max_addressable` | ↑ | `min` | лимиты ФС и таблиц |
| `stable_across_reboot` | ↑ | `and` | `by-id` против `sdX` |
| `assemblable_early` | ↑ | `and` | корень недоступен в initramfs |
| `required_alignment` | ↓ | `lcm` | выравнивание сквозь стек |
| `needs_random_write` | ↓ | `or` | ext4 требует, SMR не даёт |
| `needs_discard` | ↓ | `or` | политика TRIM из спеки |
| `must_survive_failures` | ↓ | `max` | требование к избыточности |
| `needs_bootloader_read` | ↓ | `or` | `/boot` и возможности GRUB |
| `needs_early_boot` | ↓ | `or` | что попадёт в initramfs |

Направление `↑` — синтезируемые атрибуты (снизу вверх, от физики), `↓` — наследуемые (сверху вниз, от намерения). Формально это атрибутная грамматика над DAG, и вычисляется она за один проход в каждую сторону плюс итерации до неподвижной точки там, где есть циклы по требованиям.

### 7.4 Два потока и точка встречи

```
        намерение (mount /, boot, redundancy, discard)
                        │ demand ↓
   ┌────────────────────┼────────────────────┐
   │   ФС ── LUKS ── LV ── VG ── PV ── раздел │
   └────────────────────┼────────────────────┘
                        │ offer ↑
        физика (sector size, zoned, transport, домены отказа)
```

В каждом узле выполняется проверка `offer(node) ⊨ demand(node)`. Несовместимость обнаруживается **в конкретной точке**, а не «где-то в конфигурации», и обе стороны конфликта имеют происхождение.

### 7.5 Вердикт и происхождение

Результат проверки — не булев:

```
Verdict = Ok
        | Suboptimal   // работает, но есть лучше
        | Degraded     // теряется запрошенное свойство (discard, self-healing, ёмкость)
        | Unsafe       // работает, известный риск потери данных
        | Broken       // соберётся, но не загрузится / не переживёт перезагрузку
        | Impossible   // не соберётся вообще
        | Indeterminate // не хватает данных, см. 7.8
```

Каждый вердикт несёт **цепочку происхождения** — это то, что превращает диагностику из ругательства в объяснение:

```
E_WRITE_PATTERN_CONFLICT  (Impossible)

  требование: needs_random_write = true
    ← ext4 on /dev/mapper/vg-root  [провайдер ext4]
    ← LV vg/root
    ← VG vg
    ← PV /dev/sdb1

  предложение: write_pattern = SequentialWithinZone
    ← /dev/sdb  Seagate ST20000NM  (host-managed SMR, zone 256 MiB)

  конфликт в узле: PV /dev/sdb1

  варианты: f2fs · btrfs (zoned) · dm-zoned как прослойка · другое устройство
```

UI подсвечивает оба конца цепочки и узел конфликта. Без провенанса пользователь видит «ext4 нельзя» и не понимает почему — при том что виноват диск, купленный три года назад и ничем внешне не отличающийся от обычного.

### 7.6 Домены отказа

Отдельный, первоклассный механизм. Именно он ловит топологический класс несовместимости, недоступный ни capability-проверкам, ни типизации интерфейсов.

```
FailureDomain {
  kind: Disk | Controller | Hba | Enclosure | PowerRail
      | Host | NetworkPath | SanArray | Site
  id:   String
}
```

Каждый физический узел объявляет домены, от которых зависит; вверх по графу они объединяются (`union`).

Проверка для любого узла с избыточностью `tolerated_failures = k` и множеством членов `M`:

```
∀ d ∈ ⋃ domains(M):  |{ m ∈ M : d ∈ domains(m) }| ≤ k
```

Иначе — `E_CORRELATED_FAILURE_DOMAIN` с указанием общего домена.

Что это ловит из реальной практики:

| Конфигурация | Общий домен | Вердикт |
|---|---|---|
| `md raid1` из `sda1` + `sda2` | `Disk:sda` | `Broken` — избыточности нет |
| `btrfs raid1` на двух разделах одного NVMe | `Disk:nvme0n1` | `Broken` |
| RAID из двух LUN одного SAN-массива | `SanArray:X` | `Unsafe` |
| Зеркало через два пути к одному LUN | `Disk:wwid` | `Impossible` (плюс блокировка по 5.3) |
| raidz2 из шести дисков в одной полке | `Enclosure:E1` | `Suboptimal` — предупреждение о SPOF |
| Зеркало между локальным диском и iSCSI | `Host` разный, `NetworkPath` | `Ok` по домену, но `Unsafe` по transport |

Домены заполняются из `by-path`, топологии PCIe/SCSI, вывода `multipath`, target portal для сетевых. Там, где топология недостоверна, домен помечается `inferred` и понижает вердикт до предупреждения, а не до ошибки.

### 7.7 Асимметрия избыточности

Родственный, но отдельный класс: массив избыточен, а служебный компонент — нет, и его потеря убивает всё.

Правило: для любого узла с `redundancy = R` все узлы, от которых зависит его целостность (`Journals`, `Caches` в режиме writeback, `Provides` служебного назначения), обязаны иметь `redundancy ≥ R`.

Ловит:

- ZFS `special` vdev без зеркала в пуле из raidz2 — потеря метаданных уничтожает пул
- `bcache`/`dm-writecache` в режиме writeback на одиночном SSD поверх избыточного массива
- Внешний журнал ext4/XFS на нерезервированном устройстве
- SLOG без зеркала при `sync=always`

Код `E_REDUNDANCY_ASYMMETRY`, вердикт `Unsafe`, с прямым текстом о том, что именно теряется при отказе конкретного компонента.

### 7.8 Неизвестное — не значит совместимое

Probe регулярно не знает атрибута: экзотический контроллер, сетевое устройство за таймаутом, виртуализованный диск без топологии. Двузначная логика здесь опасна в обе стороны: `unknown = ok` даёт молчаливые провалы, `unknown = error` делает бэкенд неработоспособным на половине железа.

Поэтому проверка **трёхзначна**, а `Indeterminate` — легитимный вердикт с явной политикой:

```
policy.unknown_attributes: permissive | strict | ask
```

- `permissive` (десктоп) — предупреждение, продолжаем
- `strict` (сервер, автоустановка) — ошибка
- `ask` — запрос подтверждения с перечислением того, что именно неизвестно

Обязательное требование: `Indeterminate` **никогда не схлопывается в `Ok` молча**. В отчёте всегда видно, какие проверки не были выполнены и почему.

### 7.9 Совместимость со средой: две разные среды

Критическое различие, которое пропускают почти все инсталляторы: **среда установки ≠ целевая система**.

```
FeatureRequirement {
  feature: String            // "btrfs.zstd" | "luks2.argon2id" | "zfs.draid"
  min_version: Option<Ver>
  scope: HostTools | HostKernel | TargetKernel | TargetInitramfs | Bootloader | Firmware
}
```

Граф порождает множество требований; оно проверяется против **обоих** окружений раздельно.

Что ловится только так:

- `mkfs.btrfs` из live-образа включает фичу, которую ядро целевого дистрибутива не смонтирует
- LUKS2 с Argon2id создан, но в целевой initramfs нет нужной версии cryptsetup
- Корень на NVMe-oF, а в initramfs целевой системы нет `nvme-tcp` и сетевой конфигурации
- GRUB целевой системы старше, чем требует выбранный профиль Btrfs
- Firmware — Legacy BIOS, а разметка сделана в UEFI-режиме live-образа

Требование к реализации: набор фич, порождаемых графом, — это данные, а не логика. Провайдер декларирует `features(node) -> [FeatureRequirement]`, а таблицы поддержки версионируются отдельно от кода и обновляются вместе с дистрибутивом.

### 7.10 Временная совместимость

Проверять только конечное состояние недостаточно: план проходит через промежуточные графы, и они тоже обязаны быть корректны.

Каждое действие декларирует трансформацию графа:

```
Action::effect(graph) -> Graph
```

Планировщик **типизирует состояние после каждого действия**, а не только итоговое. Отказ на промежуточном шаге — ошибка планирования, а не выполнения.

Ловит:

- Усечение раздела раньше усечения ФС
- Уменьшение ФС ниже текущего занятого объёма
- Удаление PV из VG, когда экстенты ещё не перенесены
- `btrfs balance --convert` при недостатке места для промежуточных чанков
- Временная потеря избыточности при последовательной замене дисков — с явным окном уязвимости, которое показывается пользователю

Последнее заслуживает отдельного вывода в UI: «на шагах 7–12 массив будет без избыточности примерно 40 минут».

### 7.11 Вывод типов вместо валидации: главный выигрыш для UX

Тот же движок, запущенный в обратную сторону, отвечает не «это неправильно», а «что здесь возможно»:

```
candidates(target: NodeId, role: Option<Role>) -> [Candidate]

Candidate {
  kind: NodeKind
  constraints: { min_size, max_size, required_params, ... }
  verdict: Verdict          // отсортировано: Ok → Suboptimal → Unsafe
  rationale: [Provenance]   // почему не Ok
}
```

Реализация — перебор известных `NodeKind` с проверкой `offers(kind) ⊨ demand(target)` и `offer(target) ⊨ requires(kind)`.

Эффект: **UI физически не может предложить несовместимый вариант**. На SMR-диске в списке файловых систем не окажется ext4 — не потому что UI об этом знает, а потому что бэкенд её не вернул. Список отсортирован по вердикту, варианты с `Unsafe` показаны с пометкой и обоснованием, а не спрятаны — пользователь вправе принять риск осознанно.

Это переворачивает взаимодействие: вместо «сделай, потом узнай, что нельзя» — «предлагается только то, что работает». Для инсталлятора это ровно та разница, из-за которой ручную разметку боятся.

### 7.12 Ремонт вставкой адаптера

Часть несовместимостей устраняется автоматически введением промежуточного узла. Движок ищет такие решения и предлагает их как обычный `Fix` (патч к спеке, см. 8.1):

| Конфликт | Адаптер |
|---|---|
| Случайная запись vs zoned | `dm-zoned` |
| Требуется discard, блокирован LUKS | `--allow-discards` (параметр, не узел) |
| Требуется целостность, ФС без контрольных сумм | `dm-integrity` под массивом |
| Требуется избыточность, одиночное устройство | `md raid1` при наличии свободного кандидата |
| Требуется стабильное имя | переход на `by-id`/UUID |

Правило: адаптер **никогда не вставляется молча**. Это всегда предложение с описанием последствий (падение производительности `dm-integrity`, дополнительный слой в initramfs, изменение размера).

### 7.13 Требования к реализации

- Проверка совместимости — **чистая функция** от `(Graph, Environment, Policy)`. Без обращений к системе, полностью воспроизводима на фикстуре.
- Полный вывод атрибутов — не дольше 50 мс на графе из 500 узлов; результат кэшируется и инвалидируется точечно по изменённому поддереву.
- Инкрементальность обязательна: при перетаскивании ползунка размера в UI пересчитывается только затронутая ветвь.
- Каждый атрибут, интерфейс и код вердикта документирован и имеет тест; добавление провайдера без деклараций `offers`/`requires`/`features` не проходит сборку.
- Матрица «класс несовместимости × провайдер» покрыта тестами на фикстурах, включая заведомо порочные конфигурации (зеркало на одном диске, RAID поверх iSCSI, ext4 на SMR, special vdev без резерва) — с проверкой не только факта отказа, но и **текста цепочки происхождения**.

## 8. Валидация и диагностика

### 7.1 Формат диагностики

Строк с текстом ошибок в ядре нет. Есть:

```
Diagnostic {
  code:      "E_XFS_SHRINK_UNSUPPORTED"    // стабильный, документированный
  severity:  Error | Warning | Info | Hint
  subjects:  [NodeId]                       // что подсветить в UI
  params:    { requested: 40GiB, current: 80GiB }
  message_key: "diag.xfs.shrink_unsupported"
  doc_url:   "https://.../E_XFS_SHRINK_UNSUPPORTED"
  fixes:     [Fix]
}

Fix {
  id: "convert-to-ext4"
  label_key: "fix.convert_to_ext4"
  patch: SpecPatch        // JSON Patch к спеке желаемого состояния
  consequences: [Diagnostic]   // что станет после применения
}
```

Ключевое: **fix — это патч к спеке, а не действие**. UI применяет патч, запускает переплан, показывает новый результат. Один клик, полностью обратимо, никакого специального кода в UI.

### 7.2 Классы правил

**Структурные:** ацикличность, отсутствие перекрытий разделов, соблюдение выравнивания, лимиты таблицы разделов, единственность точек монтирования.

**Загрузочные** (самый частый источник кирпичей):
- UEFI → обязателен ESP ≥ 100 МиБ, FAT32, на GPT, на том же диске, что и загрузчик
- GPT + Legacy BIOS → обязателен `bios_boot` 1 МиБ
- `/boot` на ФС, поддерживаемой загрузчиком; GRUB + Btrfs-сжатие zstd — проверка версии
- `/boot` вместимость под N ядер + initramfs, эвристика от дистрибутива, не константа
- Шифрованный `/boot` → предупреждение о производительности и требованиях к GRUB
- `/` на LVM/md/LUKS → проверка, что модули попадут в initramfs

**Возможности:** уменьшение XFS, лимиты размеров ФС, гетерогенные члены массива, `Discouraged` профили.

**Целостность и надёжность:**
- mdadm/Btrfs/ZFS-члены на сетевых или съёмных устройствах → предупреждение с объяснением про таймауты и полный ресинк
- Смешивание локальных и сетевых устройств в одном массиве → `W_MIXED_TRANSPORT_REDUNDANCY`
- ZFS: несовпадающие по размеру диски в vdev → потеря ёмкости; разные ashift → ошибка
- Btrfs RAID5/6 для данных → `W_BTRFS_RAID56_WRITE_HOLE`, требует явного подтверждения
- Все vdev пула должны иметь избыточность, иначе `W_ZFS_NONREDUNDANT_VDEV` («потеря vdev = потеря пула»)

**Порядок слоёв:**
- LUKS выше избыточности (RAID → LUKS) — рекомендуемо; обратный порядок даёт `H_CRYPT_BELOW_RAID_COST` с оценкой оверхеда CPU и объёма ресинка
- Пробрасывание discard через стек: если `discard: periodic`, а LUKS без `allow_discards` — `W_DISCARD_BLOCKED_AT_LAYER` с указанием конкретного слоя
- CoW-ФС под образы ВМ и БД → `H_COW_FRAGMENTATION` с предложением `nodatacow`

**Ёмкость и производительность:** переполнение thin-пула, `H_SWAP_TOO_SMALL_FOR_HIBERNATE`, отсутствие overprovisioning на SSD, `dup`-метаданные на SSD.

### 7.3 Требования

- Валидация запускается на **желаемом** графе, а не только на плане: пользователь видит проблему сразу при редактировании
- Полный прогон — не дольше 200 мс на графе из 500 узлов (интерактивный UI)
- Каждое правило имеет тест и запись в документации по коду ошибки
- Правила версионируются: новое предупреждение в минорной версии не должно ломать автоустановку, которая трактует warning как ошибку → политика `treat_warnings_as_errors` явно управляется в спеке

## 9. Решатель размеров

Отдельный, полностью детерминированный, чистая функция.

**Вход:** контейнер (диск/VG/пул), набор `SizeSpec`, ограничения выравнивания, оверхеды.
**Выход:** конкретные offset/size либо диагностика невозможности.

Алгоритм:
1. Вычесть служебные области (таблица разделов, метаданные, оверхеды провайдеров)
2. Разместить `Exact` и `min` из `Range` — если сумма превышает ёмкость, ошибка с точной дельтой
3. Разложить `Percent` от указанного основания
4. Распределить остаток по `weight` пропорционально
5. Применить `max`-ограничения; освободившееся вернуть в шаг 4 (итеративно, до фикспойнта)
6. Выровнять каждую границу; недостачу от округления отнести на элемент с наибольшим `weight`
7. Проверить инварианты: сумма ≤ ёмкость, нет перекрытий, все границы выровнены

Требования:
- **Детерминированность**: одинаковый вход → побайтово одинаковый выход, независимо от порядка итерации хэш-таблиц
- Покрытие property-тестами на инварианты
- При невозможности — диагностика вида «не хватает 2.3 ГиБ; уменьшите `/home` на 2.3 ГиБ или снимите `min` с `/var`» с готовыми `Fix`

## 10. Планировщик

### 9.1 Diff → Action DAG

```
Action {
  id:            ActionId
  kind:          ActionKind
  subjects:      [NodeId]
  params:        Params
  depends_on:    [ActionId]
  reversibility: Reversible | Recoverable | Irreversible
  destructive:   bool
  estimated:     { duration: Duration, io: Bytes }
  description_key: String
  params_for_display: Map            // для человекочитаемого рендера
}
```

Порядок выполнения — топологическая сортировка. Зависимости выводятся из графа автоматически (нельзя создать LV раньше VG, нельзя mkfs раньше открытия LUKS), а не задаются вручную.

Ключевые группы `ActionKind`: `Deactivate`, `Wipe`, `CreateTable`, `CreatePartition`, `ResizePartition`, `SetPartitionAttrs`, `LuksFormat`, `LuksOpen`, `AddKeyslot`, `EnrollTpm2`, `MdCreate`, `MdAdd`, `PvCreate`, `VgCreate`, `LvCreate`, `LvResize`, `PoolCreate`, `DatasetCreate`, `SubvolumeCreate`, `Mkfs`, `FsResize`, `SetFsLabel`, `Mount`, `WriteFstab`, `WriteCrypttab`, `RegenerateInitramfs`, `InstallBootloader`.

### 9.2 Точка невозврата

Планировщик вычисляет `point_of_no_return` — индекс первого действия класса `Irreversible`. Всё до неё откатывается автоматически. UI **обязан** явно запросить подтверждение перед пересечением, показав, что именно будет уничтожено:

```
Будет безвозвратно уничтожено:
  /dev/nvme0n1p3  ext4  "ubuntu-root"  420 ГиБ, изменён 2 дня назад
  /dev/sdb        весь диск, ZFS-пул "old-tank", 4 датасета
```

### 9.3 Оптимизации плана

- **Схлопывание**: `create partition → mkfs → resize` до нужного размера → сразу создать нужного размера
- **Устранение мусора**: не форматировать то, что будет удалено следующим действием
- **Параллелизация**: независимые ветви DAG выполняются одновременно (mkfs на 6 дисках — параллельно); ограничение по I/O-бюджету и по общему устройству
- **Отложенный ресинк**: `mdadm --assume-clean` там, где безопасно (свежий массив под немедленный mkfs), с фиксацией в плане как явного компромисса

### 9.4 Требования

- План сериализуем в JSON, YAML, человекочитаемый текст, DOT и в **shell-скрипт** (последнее — для аудита и для случаев, когда администратор хочет выполнить руками; скрипт снабжается комментариями и не является поддерживаемым способом выполнения)
- Планирование не выполняет никаких изменений и не требует привилегий записи
- Планирование того же спека на том же probe даёт побитово идентичный план (для golden-тестов)

## 11. Исполнитель

### 10.1 Транзакционность

- **Write-ahead journal** в `/run/storaged-ng/journal-<ulid>.json`, синхронизируется перед каждым действием. При наличии доступного персистентного хранилища дублируется туда.
- Каждое действие фиксирует: начало, параметры, результат, наблюдаемые эффекты, время.
- Прерывание (питание, краш) → при следующем запуске журнал обнаруживается, состояние сверяется с реальностью через probe, пользователю показывается отчёт «что успело выполниться» и предлагается продолжить или откатить.
- Откат `Reversible`-действий — автоматически при ошибке; для `Recoverable` — с подтверждением; `Irreversible` — только отчёт.

### 10.2 Прогресс и события

Поток событий (D-Bus signal / JSON-RPC notification):

```
{ type: "action_started",  action_id, eta_seconds }
{ type: "progress", action_id, fraction: 0.42, phase: "resync",
  rate_bytes_per_sec: 180000000, eta_seconds: 3200 }
{ type: "action_finished", action_id, effects: [...] }
{ type: "diagnostic", diagnostic: {...} }
{ type: "confirmation_required", prompt_id, kind: "destructive", details: {...} }
{ type: "credential_required", prompt_id, ref: "@prompt:disk-password" }
{ type: "graph_changed", generation: 42, delta: {...} }
```

Прогресс для долгих операций берётся из реальных источников: `/proc/mdstat`, `zpool status`, `btrfs balance status`, `resize2fs` stderr, а не аппроксимируется таймером. Для операций без прогресса честно сообщается `indeterminate`.

### 10.3 Требования безопасности выполнения

- **Проверка предусловий непосредственно перед каждым действием.** Между планированием и выполнением мог измениться мир. Несовпадение → остановка, а не «продолжим и посмотрим».
- **Generation guard**: план привязан к поколению графа; выполнение устаревшего плана без явного переплана запрещено.
- **Синхронизация с udev** после каждого изменения (`udevadm settle` с таймаутом), с обязательной проверкой появления ожидаемого узла, а не слепым `sleep`.
- **Явная активация**: LUKS/LVM/md активируются только действиями плана.
- Все действия выполняются с минимально необходимыми привилегиями; операции без привилегий (probe, plan) не требуют root.

## 12. Модель безопасности

### 11.1 Защита данных

| Механизм | Описание |
|---|---|
| Read-only по умолчанию | Запись требует явного `allow_destructive` |
| Защита используемых устройств | Смонтированные, swap, члены активных массивов, устройства с открытыми файлами |
| Защита корня | Устройство, на котором работает текущая система, требует особого флага |
| Защита чужих ОС | `Foreign` устройства требуют отдельного подтверждения с указанием, какая ОС распознана |
| Возраст данных | Показывается время последнего монтирования/изменения перед уничтожением |
| Wipe-политика | Явное разделение: `wipefs` подписи / `blkdiscard` / полная перезапись / secure erase (ATA/NVMe sanitize) |

### 11.2 Секреты

- Пароли и ключи **никогда** не попадают в журнал, логи, план, дампы probe и сообщения об ошибках. Тип `Secret<T>` с запрещённым `Debug`/`Display` и затиранием памяти при уничтожении.
- Передача через отдельный канал (fd-passing по unix-сокету, keyring), не через параметры действий.
- Логирование обязано проходить через фильтр; тест проверяет отсутствие секретов в полном логе прогона.

### 11.3 Привилегии

- Демон разделён: непривилегированная часть (probe через sysfs, планирование, валидация) и привилегированный исполнитель.
- Авторизация через polkit с гранулярными действиями (`read`, `plan`, `modify-unused`, `modify-any`, `destroy-foreign`).
- Все входные данные (спеки, патчи) валидируются по схеме до обработки.

## 13. Интеграция с загрузкой целевой системы

Бэкенд обязан не просто разметить диски, а привести целевую систему в загружаемое состояние:

- **Генерация `/etc/fstab`** с `UUID=`/`PARTUUID=`, корректными `nofail` для съёмных, `_netdev` для сетевых, `x-systemd.device-timeout`, `x-systemd.requires` для зависимостей стека
- **Генерация `/etc/crypttab`** с корректными опциями (`discard`, `tpm2-device=auto`, `keyfile`, `initramfs`)
- **Поддержка Discoverable Partitions Spec**: при соблюдении требований DPS предлагать минимальный `fstab` (или его отсутствие) с корректными типами GUID
- **Список модулей для initramfs**, вычисленный из графа: `dm-crypt`, `raid456`, `btrfs`, `nvme-tcp`, драйверы iSCSI и т.д. — с учётом того, что для сетевого корня нужна ещё и сетевая конфигурация в initramfs
- **Проверка загружаемости как отдельная операция** (`verify-bootable`), которую можно запустить после установки

## 14. Контракт визуализации

Отдельный, стабильный, специально спроектированный API. UI не должен реконструировать структуру из сырого графа.

### 13.1 Три проекции

**A. Stack View** — привычные «полоски» по устройствам:

```
LayoutView {
  columns: [ Column {
    root: NodeId,
    layers: [ Layer {
      depth: u8,
      segments: [ Segment {
        node: NodeId, offset: Bytes, size: Bytes,
        label: DisplayLabel, badges: [Badge], fill: FillHint,
        significance: Major | Minor | Negligible
      }]
    }]
  }]
}
```

`significance` решает вечную проблему: раздел BIOS boot в 1 МиБ рядом с диском на 20 ТБ невидим при честном масштабе. Бэкенд помечает, что сегмент требует минимальной визуальной ширины, но **не диктует пиксели** — масштаб остаётся за UI.

**B. Graph View** — полный DAG с рассчитанными топологическими уровнями и стабильным порядком узлов внутри уровня (детерминированная сортировка), чтобы при перерисовке узлы не прыгали.

**C. Mount Tree** — дерево точек монтирования с привязкой к узлам, для проверки «что куда встанет».

### 13.2 Общие требования

```
Badge = Encrypted | Redundant(level) | Degraded | Removable | Network | ReadOnly
      | Zoned | Compressed | Snapshot | Cached | Foreign | New | ToBeDestroyed
      | Experimental | Discouraged
```

- **Все подписи — ключи локализации + параметры**, не готовые строки. Бэкенд не знает языка.
- **Стабильные ID** между вызовами; `planned:` алиасится на реальный после выполнения
- **Дельта-обновления**: при `graph_changed` отдаётся патч, а не полная перерисовка
- **Цвета не задаются бэкендом.** Отдаётся `FillHint` — семантическая категория (`data`, `system`, `swap`, `free`, `foreign`, `metadata`), палитра — дело темы UI
- **Встроенные рендереры** для паритета: ASCII-дерево, таблица, DOT/Graphviz, Mermaid. Всё, что видит GUI, доступно в CLI.

### 13.3 Пример ASCII-рендера

```
nvme0n1  1.8 TiB  Samsung 990 PRO                    [SSD]
├─ p1     1 GiB   ESP           vfat      → /efi     [NEW]
├─ p2     2 GiB   boot          ext4      → /boot    [NEW]
└─ p3   1.8 TiB   luks2 ────────────────────────────  [ENCRYPTED · TPM2]
        └─ cryptroot  btrfs  zstd:1                   [COMPRESSED]
           ├─ @          → /
           ├─ @home      → /home
           └─ @snapshots → /.snapshots

tank  ZFS pool  72 TiB usable                    [REDUNDANT · DEGRADED]
├─ raidz2  6 × 18 TiB  ─ sd{b,c,d,e,f,g}
│  └─ sdf  FAULTED — заменить                    [!]
└─ special mirror  2 × 2 TiB  nvme{1,2}n1
```

## 15. Публичный API

| Поверхность | Назначение |
|---|---|
| **Rust crate** | Каноническая реализация, всё остальное — обёртки |
| **C ABI** | Для интеграции в существующие инсталляторы на C/C++ |
| **D-Bus** | Системный демон, интеграция с DE, polkit |
| **JSON-RPC over unix socket** | Для инсталляторов и контейнеризованных клиентов |
| **CLI** | Полный паритет функциональности, `--json` на каждой команде |
| **Python/Go bindings** | Генерируются из C ABI |

Базовые операции:

```
probe [--refresh] [--fixture FILE]           → Graph
export [--format yaml]                       → Spec
validate SPEC                                → [Diagnostic]
plan SPEC [--from-fixture FILE]              → Plan
explain PLAN [--format text|dot|mermaid|sh]  → рендер
apply PLAN [--yes] [--stop-before-irreversible]
resume [JOURNAL]
verify-bootable [--target /mnt]
view [--stack|--graph|--mounts] [--format ascii|json]
```

**Семантическое версионирование** для всех форматов: `Spec`, `Plan`, `Graph`, коды диагностик. Формат плана, созданного версией N, должен читаться версией N+1 или отвергаться с внятным сообщением, но не интерпретироваться неверно.

## 16. Динамика: hotplug и переплан

Именно ради этого спека декларативна.

1. Событие udev/netlink → инкрементальный probe → `generation++`
2. Если есть активный план, он помечается `Stale` с описанием дельты
3. Планировщик **автоматически перерешает** спеку на новом графе
4. Клиенту отдаётся `PlanDiff`: что изменилось в плане, какие новые диагностики появились, какие исчезли
5. UI показывает изменение, а не молча подменяет план

Обязательные сценарии:

| Событие | Ожидаемое поведение |
|---|---|
| Вставлена флешка | Появляется в графе, не участвует в спеке без селектора, не ломает план |
| Извлечён диск из плана | План → `Invalid`, конкретное действие подсвечено, предложены `Fix` |
| Сетевой таргет отвалился | Узлы → `Missing`, выполнение приостанавливается, а не падает |
| Сетевой таргет вернулся | Автоматическое восстановление состояния узлов, продолжение по подтверждению |
| Диск подключён во время выполнения | Игнорируется до конца текущего плана (generation guard) |

## 17. Наблюдаемость

## 18. Тестирование

Это не приложение к ТЗ, а часть требований. Ошибка в таком бэкенде стоит пользователю всех данных.

| Уровень | Содержание |
|---|---|
| **Unit** | Решатель размеров (property-тесты на инварианты), выравнивание, парсеры вывода утилит на зафиксированных выводах разных версий |
| **Golden** | `(fixture, spec) → plan`, сравнение с эталоном. Любое изменение плана видно в code review |
| **Fixtures** | Библиотека реальных дампов probe: ноутбук, dual-boot, SAN с multipath, JBOD на 24 диска, SMR, деградировавший массив, битые таблицы разделов |
| **Loop-based** | Полный цикл на loop-устройствах — быстро, в обычном CI, без привилегий на железо |
| **VM matrix** | QEMU: UEFI/BIOS, NVMe, zoned NVMe, iSCSI-таргет, multipath (два пути к одному образу), реальная загрузка после установки |
| **Fault injection** | Прерывание на каждом шаге плана → проверка журнала, восстановления, отсутствия потери данных сверх ожидаемого |
| **Fuzzing** | Спеки, патчи, повреждённые суперблоки и таблицы разделов |
| **Совместимость** | Матрица версий `util-linux`, `lvm2`, `mdadm`, `cryptsetup`, `btrfs-progs`, `zfs`, `xfsprogs` — минимум по две поддерживаемые версии каждого |

**Критерий приёмки для каждого сценария из матрицы VM: система реально загружается после установки.** Не «команды отработали без ошибок».

## 20. Этапы

**M1 — Ядро.** Граф, типы, идентичность, probe локальных устройств, GPT/MBR, ext4/XFS/swap, решатель, планировщик, executor с журналом, CLI, ASCII-рендер.

## Приложение A. Инварианты, проверяемые всегда

1. Граф ацикличен
2. Ни один диапазон `Contains` не перекрывается с другим на том же родителе
3. Сумма размеров детей + служебные области ≤ размер родителя
4. Все границы выровнены по объединённому требованию цепочки
5. Каждый узел с `NodeState::Present` достижим из физического устройства либо является виртуальным по природе (zram, tmpfs)
6. Ни один `Path`-узел multipath не используется напрямую
7. Каждая точка монтирования уникальна в пределах целевой системы
8. Каждый узел, участвующий в плане, существует в графе того же поколения
9. Секреты не присутствуют ни в одном сериализуемом объекте
10. `planned:`-идентификаторы отсутствуют в графе после успешного выполнения плана
11. Для каждого ребра выполняется `offer ⊨ demand`; вердикт не ниже разрешённого политикой
12. Ни один домен отказа не покрывает больше членов агрегата, чем тот способен пережить
13. Служебные компоненты (журнал, writeback-кэш, special vdev) не менее избыточны, чем защищаемые ими данные
14. Каждое промежуточное состояние плана проходит ту же типовую проверку, что и конечное
15. Множество требуемых фич удовлетворяется **обеими** средами — установочной и целевой
16. Ни один вердикт `Indeterminate` не схлопнут в `Ok` без записи в отчёте
17. Probe никогда не порождает malformed-граф; любая нарушающая ожидания реальность выражается через `Anomaly`
18. `Plan` не может быть построен иначе как из `Checked<Graph>`; токен недействителен при смене среды, политики или поколения графа

Инварианты 1–4 и 9 проверяются **на входе** (нарушение = отказ построения). Остальные — **на проверке** (нарушение = диагностика). Различие принципиально: см. 2.7.

## Приложение C. Существующие реализации в open source

Раздел отвечает на вопрос «не изобретаем ли мы велосипед» и фиксирует, что можно переиспользовать, а что действительно новое. Краткий ответ: ядро модели изобретено до нас и подтверждено практикой, но ни один проект не покрывает связку целиком, и все ключевые механизмы главы 7 отсутствуют везде.

### C.1 libstorage-ng — ближайший аналог

Библиотека YaST (C++, openSUSE/SUSE), пришедшая к тому же ядру независимо:

- Информация об устройствах хранится **в графе, а не в списках** — прямой аналог главы 2
- Сравниваются **два графа** — текущей системы и staging; из разницы строится граф действий с зависимостями в рёбрах, порядок даёт топологическая сортировка — глава 10 практически дословно
- Обоснование совпадает: проверять зависимости надёжнее, чем порядок, потому что верный порядок может получиться случайно; та же сортировка показывает, что допустимо выполнять параллельно
- В целях проекта зафиксировано предпочтение проверок времени компиляции — то есть развилку из 2.7 там обдумывали
- Умеет выгружать графы действий в graphviz — зачаток контракта визуализации

**Чего нет:** системы типов и вывода атрибутов (совместимость — россыпь частных проверок), доменов отказа, ZFS, разделения установочной и целевой среды, обратного режима `candidates()`, журнала с продолжением. Биндинги через SWIG вынуждают вызывающий код к явным приведениям типов; API намеренно не скрывает структуру, что при отсутствии типовой проверки перекладывает всю ответственность на потребителя.

**Вывод:** главы 2 и 7 технически возможно принести в libstorage-ng как надстройку — модель уже почти подходит.

### C.2 blivet — самый долгоживущий

Python-библиотека Red Hat, бэкенд Anaconda, blivet-gui и Ansible-роли `linux-system-roles/storage`.

Сильные стороны: планирование произвольно большой серии действий в памяти с наблюдаемым эффектом каждого и записью на диск только при явном выполнении; `DeviceFactory` для создания целых стеков одним вызовом; развитый аллокатор разделов по гибким спецификациям.

**Ограничение принципиальное:** `DeviceTree` — дерево. Все случаи из 2.1 (VG из нескольких PV, многодисковый Btrfs, zvol с собственным стеком, два входа bcache) ложатся плохо и требуют обходных конструкций.

### C.3 Agama — ближайший аналог главы 6

Новый инсталлятор SUSE. Декларативный JSON-профиль с селекторами существующих устройств, включая сортировку — например, «собрать MD RAID из двух самых больших дисков системы». Это ровно механизм `@primary` из главы 6. Один и тот же алгоритм обслуживает интерактивную и автоматическую установку, а опущенные части конфигурации выводятся автоматически из свойств системы и целевого продукта — прямой аналог `Auto` в `SizeSpec` и ролей.

Ядро на Rust, но работа с хранилищем делегируется yast2-storage-ng и далее libstorage-ng.

### C.4 systemd-repart — ближайший аналог главы 9

Решатель размеров почти совпадает с нашим: размещение в свободных областях с учётом минимума, максимума, веса и приоритета; при нехватке места отбрасываются определения по приоритету, причём нулевой приоритет не отбрасывается никогда. Плюс идемпотентность (безопасно запускать при каждой загрузке), dry-run, несопоставленные разделы сохраняются как чужие, атомарное обновление таблицы, LUKS2 с привязкой к TPM2, dm-verity, генерация образов.

**Ограничения принципиальные:** только GPT; только рост и добавление — никогда сжатие, удаление или перемещение; ни LVM, ни RAID, ни ZFS; графа нет вовсе.

### C.5 disko — самое полное декларативное покрытие

Nix-модуль: GPT, LVM, LUKS, Btrfs, ZFS, bcachefs, mdadm в одном описании. Модель вложенная (`content` внутри `content`) — снова дерево. Переформатирует диск целиком, перезаписывая существующее; двойная загрузка не поддерживается, то есть **diff против реальности отсутствует как концепция**. Валидатора и обратного режима нет.

### C.6 udisks2 + libblockdev

Архитектура «плагин на технологию» — буквально реестр провайдеров из главы 4. `libblockdev` покрывает LVM, md, LUKS, ФС, loop, NVMe и остаётся лучшим кандидатом на слой системных адаптеров. `udisks2` — runtime-сервис с D-Bus API, планирования не имеет.

| Проект | Роль | Модель |

### C.8 Сводка: чего нет ни у кого

| Механизм ТЗ | Раздел | Существует |
|---|---|---|
| Вывод атрибутов вверх/вниз, `offer ⊨ demand` | 7.2–7.4 | нет |
| Домены отказа на уровне хоста | 7.6 | нет |
| Асимметрия избыточности | 7.7 | нет |
| Трёхзначность при неизвестных атрибутах | 7.8 | нет |
| Установочная среда ≠ целевая | 7.9 | нет систематически |
| Типизация промежуточных состояний плана | 7.10 | нет |
| Обратный режим `candidates()` | 7.11 | нет |
| Разграничение malformed / invalid + аномалии | 2.7 | частично (blivet, libstorage-ng) |
| ZFS и блочный стек в единой модели | 3 | нет |
| Журнал с продолжением после сбоя | 11.1 | нет |
| Контракт визуализации как отдельный API | 14 | нет |

**Отдельно о доменах отказа.** Концепция существует и хорошо отработана — CRUSH в Ceph с иерархией `host`/`rack`/`row`/`datacenter`. Её просто никто не спустил на уровень одного хоста, хотя ошибка «зеркало из двух разделов одного диска» относится к тому же классу и совершается на порядки чаще, чем ошибки размещения реплик в кластере.

### C.9 Почему сложилось именно так

Каждая реализация привязана к инсталлятору одного дистрибутива, и стимула к общему решению не возникало: SUSE вкладывается в libstorage-ng, Red Hat в blivet, Canonical в curtin, systemd закрывает только образный сценарий, disko — только Nix. Дополнительный фактор: CDDL удерживает ZFS за пределами любой общей библиотеки, которую хочет линковать GPL-инсталлятор, поэтому ZFS всюду оказывается отдельным контуром.

### C.10 Следствие для реализации

Писать стек целиком с нуля бессмысленно:

- **Слой адаптеров (глава 4)** — `libblockdev`, `libblkid`, `libfdisk`, `libdevmapper`, `libzfs`
- **Решатель размеров (глава 9)** — заимствовать семантику `systemd-repart` (min/max/weight/priority с отбрасыванием), она проверена в проде
- **Язык спецификации (глава 6)** — ориентироваться на схему Agama, включая селекторы с сортировкой
- **Граф и действия (главы 2, 10)** — подтверждено libstorage-ng, воспроизводить осознанно

Действительно новое и составляющее ценность проекта — **главы 7 и 2.7**: система типов над графом, домены отказа, проверка двух сред, обратный режим вывода и разграничение malformed/invalid. Это компактное ядро поверх существующих библиотек, а не переписывание мира.
