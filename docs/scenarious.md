# Планируемые сценарии pdisks

Этот документ — черновой список пользовательских сценариев, а не утверждённое
ТЗ. Спорные сценарии явно помечены, чтобы их можно было удалить до реализации.

## 1. Базовый цикл работы

### 1.1. Просмотр текущего состояния

1. Пользователь запускает обнаружение хранилищ.
2. `pdisks` собирает `CurrentState`: граф устройств, текущие mounts,
   окружение и диагностику.
3. Повреждённые и неизвестные объекты остаются видимыми в графе.
4. Неполные данные отражаются диагностикой, а не заменяются выдуманными
   значениями.

### 1.2. Подготовка желаемого состояния

1. `DesiredState` создаётся на основе текущего графа.
2. Пользователь меняет topology, mounts или boot configuration.
3. Отдельные одноразовые операции добавляются как `OperationIntent`.
4. До выполнения пользователь получает полный план и перечень разрушительных
   последствий.

### 1.3. Изменение окружения до выполнения

1. После построения плана диск исчезает, появляется новое устройство либо
   меняется mount.
2. `pdisks` повторно проверяет затрагиваемые объекты.
3. Устаревший план не выполняется молча.
4. Пользователь получает диагностику и строит новый план.

## 2. Обычные диски и разделы

### 2.1. Установка на пустой диск

- создать GPT или MBR;
- создать разделы с корректным выравниванием;
- создать файловые системы и swap;
- назначить mounts;
- при необходимости подготовить загрузку;
- после выполнения повторно обнаружить и проверить результат.

### 2.2. Изменение существующей разметки

- увеличить или уменьшить раздел вместе с верхним слоем;
- не перемещать данные без явной поддержки provider;
- показать, какие файловые системы будут размонтированы;
- остановиться, если фактическая геометрия изменилась после планирования.

### 2.3. Сохранение чужих данных

- показать Windows, macOS и неизвестные signatures;
- по умолчанию сохранить неизвестные разделы;
- разрешить независимые операции на другом устройстве;
- требовать отдельного подтверждения для перезаписи неизвестного содержимого.

## 3. Составные хранилища

### 3.1. LUKS

- создать контейнер и mapping;
- открыть существующий контейнер;
- разместить файловую систему или LVM поверх mapping;
- закрывать mapping только после освобождения пользователей;
- не хранить ключевой материал в `DesiredState`, плане или журнале.

### 3.2. LVM

- создать PV, VG и обычный LV;
- создать striped или native RAID LV;
- изменить размер поддерживаемого LV;
- создать thin pool и thin LV;
- заменить или вывести PV с проверкой размещённых extents;
- активировать и деактивировать объекты явно.

### 3.3. MD RAID

- создать массив из выбранных members;
- собрать безопасно обнаруженный существующий массив;
- добавить, удалить или заменить member;
- дождаться завершения критичной синхронизации;
- не применять `--force` к dirty или degraded массиву автоматически.

### 3.4. Btrfs

- создать single- или multi-device filesystem;
- создать и удалить subvolume;
- назначить default subvolume;
- смонтировать выбранный subvolume;
- добавить, удалить или заменить устройство;
- явно запустить balance или изменение allocation profiles;
- запустить безопасный check или scrub;
- не запускать `btrfs check --repair` автоматически.

### 3.5. ZFS

- обнаружить pool, vdev, dataset и zvol;
- создать или импортировать pool явной операцией;
- создать dataset, zvol, snapshot или clone;
- заменить поддерживаемый vdev;
- запустить scrub;
- перед root-on-ZFS проверить kernel modules, initramfs и boot path.

## 4. Mount scenarios

### 4.1. Несколько mounts одной файловой системы

Одна файловая система используется как источник для нескольких mount points.
`MountSpec` хранит отдельную запись для каждого mount, не дублируя узел
файловой системы в `NodeGraph`.

### 4.2. Иерархические mounts целевой системы

1. Смонтировать target root в `/mnt`.
2. Смонтировать `/boot` внутри target root.
3. Смонтировать ESP как `/boot/efi` внутри того же target root.
4. Не интерпретировать эти пути как `/boot` и `/boot/efi` live-хоста.

### 4.3. Временный mount

Объект монтируется только на время установки или обслуживания. Запись есть в
runtime plan, но не добавляется в постоянную конфигурацию целевой системы.

### 4.4. Постоянный mount

Mount создаётся сейчас и записывается в конфигурацию target system. Источник
должен ссылаться на устойчивую identity, а не случайное имя `/dev/sdX`.

### 4.5. Bind, tmpfs и network mounts

- bind mount использует проверенный путь в правильном root context;
- tmpfs не требует узла в storage graph;
- NFS и CIFS представлены типизированным источником;
- управление подключением network-backed block devices пока не предлагается.

## 5. Boot scenarios

### 5.1. UEFI

- выбрать root filesystem и ESP;
- проверить тип и файловую систему ESP;
- проверить mount ESP внутри target root;
- установить bootloader;
- сформировать initramfs для target kernel;
- менять NVRAM только при явном разрешении;
- отдельно выбирать установку removable fallback path.

### 5.2. BIOS с MBR

- выбрать root filesystem;
- выбрать диск установки bootloader;
- сформировать initramfs для target kernel;
- проверить загрузку целевой системы после установки.

### 5.3. BIOS с GPT

- выполнить требования BIOS-сценария;
- дополнительно проверить BIOS Boot Partition, если она нужна bootloader;
- не подменять её обычным filesystem partition.

### 5.4. Storage-only операция

Если изменение не управляет загрузкой, используется `BootSpec::Unmanaged`.
`pdisks` не переписывает bootloader, initramfs и NVRAM побочным эффектом.

## 6. Явные операции

### 6.1. Reformat — обязательный intent

Существующая ext4 форматируется заново как ext4. До и после операции граф может
выглядеть одинаково, но содержимое будет уничтожено. Поэтому операция не может
быть восстановлена только из diff графа.

### 6.2. Check — обязательный intent

Пользователь просит проверить filesystem или другой поддерживаемый объект без
изменения его topology. Финальный граф не содержит признака выполненной
проверки.

### 6.3. Repair — обязательный intent

Пользователь отдельно разрешает поддерживаемое восстановление. Repair не
запускается как автоматическое продолжение check и требует provider-specific
проверок безопасности.

### 6.4. SetActivation — условный intent

Нужен, если пользователь хочет изменить только runtime activation, не меняя
постоянную topology: открыть mapping, активировать VG/LV или остановить массив.
Если activation станет частью декларативной модели, отдельный intent можно
удалить.

### 6.5. ReplaceMember — условный intent

Итоговый граф показывает замену старого member новым, но intent позволяет
потребовать нативную безопасную операцию replacement вместо независимых
remove/add. Оставлять только для providers, где это различие реально влияет на
сохранность данных.

### 6.6. ConvertBtrfsProfiles — спорный intent

Изменение profiles уже видно в desired graph. Отдельный intent нужен только
если пользователь должен явно выбрать balance/conversion независимо от
желаемого состояния. Иначе операцию следует вывести из graph diff.

## 7. Диагностика и отказоустойчивость

### 7.1. Неполное обнаружение

- команда probe отсутствует или завершилась ошибкой;
- часть topology известна, часть нет;
- доступные узлы остаются в snapshot;
- `MissingInformation` запрещает только операции, которым недостаёт данных.

### 7.2. Mount или holder мешает операции

- план показывает все зависимые mounts и holders;
- unmount или deactivation являются явными шагами;
- после неудачного освобождения destructive operation не продолжается.

### 7.3. Неизвестный результат операции

- процесс был прерван во время format, resize или member replacement;
- действие не повторяется автоматически;
- выполняется повторный probe;
- дальнейшее решение принимается по фактическому состоянию и журналу.

### 7.4. Замена устройства во время работы

- совпадение `/dev` path не считается совпадением identity;
- перед записью повторно проверяется выбранное устройство;
- операция останавливается при несовпадении устойчивых идентификаторов.

## 8. Пока вне предлагаемого scope

- автоматическое исправление повреждений без отдельного intent;
- произвольные shell-команды как часть публичной модели;
- автоматическое управление iSCSI, NVMe-oF, NBD и RBD connections;
- DRBD peer lifecycle и разрешение split-brain;
- автоматическая перезапись boot configuration live-хоста;
- хранение secrets внутри graph, desired state или action plan.
